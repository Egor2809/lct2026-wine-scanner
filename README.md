# Сканер российских вин «Своё вино»

[![ci](https://github.com/Egor2809/lct2026-wine-scanner/actions/workflows/ci.yml/badge.svg)](https://github.com/Egor2809/lct2026-wine-scanner/actions/workflows/ci.yml)

Кейс №10 РСХБ, ЛЦТ-2026. Фото винной этикетки → одна карточка вина из
каталога платформы «Своё вино».

```
POST /scan   multipart/form-data, поле image
→ {"slug": "oleg", "confidence": 0.99, "confident": true, "card": {...}, "analogs": [...]}
```

Ключ `slug` лежит **в корне** ответа — так его читает скрипт оценки
кейсодержателя (проверено оригинальным `participant_test.sh`). Сервис всегда
возвращает лучший slug и никогда `null`. Алиасы `/v1/eval/predict` и
`/predict` — тот же обработчик.

## Точность

Замер на публичных полевых фото кейса, в которых вино есть в каталоге
(63 фото, 44 вина; ещё 37 фото — вина вне каталога, они идут в калибровку).

**Что дал каждый шаг** (`scripts/eval_offline.py`, 23.09, до геометрии SIFT;
итоговые цифры — в таблице боевой конфигурации ниже):

| Конфигурация | top-1 | top-1 с близнецами¹ | top-5 |
|---|---|---|---|
| Baseline заказчика | 60 % | — | — |
| SigLIP 2 zero-shot + кроп (исходный каталог с ошибками фото) | 69 % | 72 % | 75 % |
| SigLIP 2 + кроп, **вычищенный каталог** | 81 % | 87 % | 92 % |
| + текст этикетки (OCR → карточка) | 86 % | 92 % | 98 % |
| + LoRA на запросах | 94 % | 98 % | 100 % |

¹ Каталог содержит карточки-близнецы с одинаковыми названием и винодельней
(`…-czitron-shardone` и `…-czitron-shardone-1`); сравнение slug у
кейсодержателя нечёткое.

**Честная оговорка.** LoRA-адаптер обучен на 48 из этих 63 фото. На 15 фото,
которых он не видел, конфигурации с текстом без LoRA и с LoRA дали 23.09
одинаково — 93 % (в боевой конфигурации 25.09 — 15/15). Поэтому ожидаемая точность на незнакомых винах ~90 %, на винах, уже
встречавшихся на полке, — выше. Без текстового канала LoRA на незнакомых фото
хуже базовой модели (73 % против 87 %) — текст обязателен.

**Боевая конфигурация, замер 25.09** (Yandex OCR из кэша, + геометрическая
проверка SIFT на пэкшотах; судья — локальный стенд команды поверх того же
`ScannerPipeline.rank()`, в репозиторий не входит):

| Набор | top-1 | macro F1 |
|---|---|---|
| Полевые фото, 63 | 96,8 % (61/63; 100 % с близнецами¹) | 0,945 |
| из них вне обучения LoRA, 15 | 100 % | 1,000 |
| Скрытая синтетика из фото каталога, 300 | 92,7 % (278/300; было 64,7 %) | 0,876 |

Латентность в судье, без HTTP: p95 0,84 с (локальная часть 0,39 с + Yandex
OCR 0,46 с). Сквозная через HTTP, как её меряет скрипт кейсодержателя, — в
разделе «Устойчивость и латентность» (p95 1,22 с на Mac). Прирост на синтетике
дала геометрия SIFT: синтетика — искажённые копии эталонов каталога, поэтому
на реальных фото прирост может быть меньше. На полевых фото геометрия
ничего не отнимает (на снимках с полки она выключена).

**В контуре, без платных API и без сети — основная конфигурация, замер 29.09.**
Рекомендуемый организаторами формат: всё работает локально на CPU. Текстовый
канал — RapidOCR (PP-OCRv5 `eslav`, кириллица, ONNX Runtime), он ставится через
pip на любой ОС; Yandex не вызывается. Живой
`ScannerPipeline.rank()` на полевых фото, OCR считается на каждом запросе:

| Конфигурация | полевые 63 | mF1 | вне обучения LoRA, 15 | синтетика 300 | p95 |
|---|---|---|---|---|---|
| только картинка (было до 29.09 в Docker без ключа) | 81,0 % | — | 73,3 % | — | — |
| + RapidOCR | 92,1 % (58/63) | — | 93,3 % | — | 0,95 с |
| + двойники букв, вес текста 0,6 | 93,7 % (59/63) | 0,891 | 100 % | 92,3 % | 0,95 с |
| **+ второй проход по верху и низу этикетки** | **96,8 % (61/63; 100 % с близнецами)** | **0,945** | **100 %** | 91,7 % | 1,64 с |
| для сравнения: Yandex OCR (25.09) | 96,8 % (61/63) | 0,945 | 100 % | 92,7 % | 0,84 с |

В Docker (`--cpus=4 --memory=4g`, linux/arm64 на том же Mac, CPU без MPS),
63 полевых фото через HTTP (`scripts/evaluate.py`), без ключа:

| Конфигурация контейнера | top-1 | p50 | p95 |
|---|---|---|---|
| **по умолчанию**: 2 прохода OCR, бюджет текста 6 с, потоки 3×1 + 2 | **95,2 %** (60/63) | 4,7 с | 6,1 с |
| 1 проход OCR, вход 1024 px, 3 потока | 92,1 % | 2,5 с | 3,0 с |
| бюджет текста 2,4 с (OCR не успевает — только картинка) | 81–82 % | 2,5 с | 2,5 с |

В контейнере SigLIP считается на CPU и делит 4 ядра с OCR, поэтому запрос
дольше, чем на Mac. Бюджет текста — жёсткий потолок: не успел OCR — ответ по
картинке, запрос не доходит до лимита скрипта проверки (10 с). Если нужна
скорость: `text.rapid_tiles: false`, `text.max_side: 1024`, `text.rapid_threads: 3`.

Второй проход (`text.rapid_tiles`): верхние и нижние 60 % кропа, увеличенные
в 1,6 раза, читаются параллельно с кадром целиком — детектор на целом кадре
теряет мелкий шрифт. На синтетике он стоит 2 фото из 300 (277 -> 275), на
реальных полевых даёт +2. Проверялись и не дали прироста: порог уверенности
строки 0,3, второй распознаватель `cyrillic`, другие параметры матчера.

Локальный OCR читает стилизованную кириллицу похожими буквами других
алфавитов: `CAMAPA`, `Py6uH`, `ОΛΕΓ` («Олег»). `TextMatcher` пробует для
таких слов кириллическое прочтение и берёт то, что ложится на словарь
каталога (`search/rerank/text_match.py`).

**Дообучение на синтетике** (`scripts/train_query_head.py`). Своих фото вин у
команды нет, поэтому обучающие кадры собираются из эталонов каталога: бутылка
вырезается с фона, кладётся на размытый кусок реальной полки (фото вин вне
каталога из датасета кейса) и искажается под съёмку в магазине. Дальше тот же
YOLO-кроп, что и в сервисе. Голова поверх замороженного SigLIP 2 (InfoNCE
против индекса) на винах, которых не было в обучении, поднимает синтетику
с 66,5 % до 79,0 %. На реальных полевых фото эффекта нет (81,0 % → 81,0 %),
поэтому в боевой конфигурации она выключена (`embedder.siglip.query_head`).
Разрыв «синтетика ↔ реальная съёмка» закрывают только реальные фото с полки.

**Все дообученные веса воспроизводятся из репозитория** — скрипты, разметка и
сплиты в `training/`, подробности в ARCHITECTURE.md, «Дообучение»:

```bash
pip install -r requirements-train.txt -c constraints.txt
python scripts/train_label_detector.py --out artifacts/models/label_yolov8n.pt  # YOLOv8n, ~20 мин на CPU
python scripts/train_lora.py --out artifacts/models/siglip_lora_v2.pt          # LoRA SigLIP 2, ~15 мин на MPS
python scripts/train_query_head.py embed && python scripts/train_query_head.py train  # голова запросов
```

## Проверка организаторами (Docker, одна команда)

Требования: Docker 24+ с Compose 2.24+, 4+ ядра CPU, 8 ГБ RAM, ~7 ГБ диска.
GPU не нужен. Образ собирается под процессор машины (amd64 или arm64), всё
нужное внутри: каталог, превью фото для карточек, индекс, SIFT эталонов,
YOLO-детектор этикетки, LoRA, веса SigLIP 2 и модели RapidOCR (скачиваются
**при сборке**). После сборки сети не нужно: всё работает в контуре.

```bash
docker compose up -d --build   # сборка ~10–15 мин один раз, старт ~20–40 с
docker compose ps              # ждать (healthy)
curl -s localhost:8080/health  # {"status":"ok","catalog_size":2103,"index_size":2099,"index":"numpy",...}
```

**Сервис работает в контуре: без Yandex, без платных API и без сети.** Текст
этикетки читает локальный RapidOCR (`text.kind: rapid` в `config/config.yaml`,
по умолчанию); ключи не нужны, `.env` не нужен. Yandex Vision OCR оставлен
опцией: `text.kind: auto` и ключ в `.env` (`YANDEX_API_KEY`, `YANDEX_FOLDER_ID`).
Порт на хосте меняется через `HOST_PORT` в `.env`.

**Стек заказчика — индекс в PostgreSQL + pgvector** (тот же образ, плюс база):

```bash
docker compose -f docker-compose.yml -f docker-compose.pgvector.yml up -d --build
curl -s localhost:8080/health  # ... "index":"pgvector" ...
```

На первом старте индекс переносится из `artifacts/index.npz` в таблицу (~5 с),
дальше поиск идёт через HNSW. На синтетике из фото каталога точность та же,
что с NumPy-индексом (60 фото: top-1 86,7 %, top-5 96,7 % в обоих режимах),
задержка выше на ~20 мс. Устройство — ARCHITECTURE.md, «Перенос на стек заказчика».

API описан в OpenAPI: `http://127.0.0.1:8080/docs`, схема ответа — `ScanResponse`.

**Запрос** — `POST /scan` (алиасы `/v1/eval/predict`, `/predict`), фото в
`multipart/form-data` (поле `image` или любое другое) либо сырым телом:

```bash
curl -s -F image=@photo.jpg localhost:8080/scan | python -c "import sys,json; print(json.load(sys.stdin)['slug'])"
```

Ответ всегда `200` с непустым `slug` в корне JSON, в том числе для битого
файла или сбоя модели (тогда `confidence: 0` и поле `error`). `4xx` — только
для невалидного запроса: пустое тело или нечитаемая multipart-форма (`400`),
файл больше 100 МБ (`413`). До конца прогрева моделей сервис не отвечает, а
если старт не удался — `503` с причиной в `/health`.
Поддерживаются JPEG, PNG (с альфой), WebP, HEIC, фото до 100 МБ.

**Прогон своего набора** — любой скрипт, запросы последовательно. Наш стенд
с порогами приёмки (код выхода 1 при провале):

```bash
python scripts/evaluate.py --labels path/to/labels.csv --url http://127.0.0.1:8080/scan \
    --wait 180 --min-top1 0.952 --max-p95 1500
# labels.csv: image,slug — путь к фото (относительно CSV) и эталонный slug
```

### Устойчивость и латентность

- Модель и индекс грузятся в lifespan; `/health` отвечает `200` только после прогрева.
- Yandex OCR: весь вызов вместе с повторами (429, 5xx, таймаут, сеть)
  укладывается в 1,6 с, запросы к облаку разнесены на 1 с (квота). После
  двух сбоев подряд облако выключается на 30 с (после 429 — на 3 с, после
  401/403 — до перезапуска). Запасной канал — локальный OCR: Apple Vision на
  macOS, RapidOCR на Linux/Windows. Вся текстовая ветка ограничена 2,4 с.
  Каждый сценарий покрыт тестом с моком: `pytest tests/test_robustness.py`.

Прогон `scripts/evaluate.py` по 63 полевым фото через HTTP, холодный старт,
два прогона подряд, Yandex OCR, 25.09.2026:

| Среда | top-1 | ошибок / null | p50 | p95 | max | первый запрос | старт |
|---|---|---|---|---|---|---|---|
| macOS, M-серия, MPS | 96,8 % / 96,8 % | 0 / 0 | 1,02 с | 1,22 с | 1,9 с | 1,1 с | 13 с |
| Docker linux/arm64 (нативно на том же Mac, CPU) | 96,8 % / 96,8 % | 0 / 0 | 1,4–1,9 с | 2,2–4,1 с¹ | 4,5 с¹ | 2,0 с | 11 с |
| Docker linux/amd64 из чистого клона (эмуляция Rosetta, CPU) | 96,8 % / 95,2 %³ | 0 / 0 | 3,6–5,0 с² | 6,0 с² | 6,6 с² | 3,6 с² | 21–41 с |
| Docker, без сети и без ключа (до 29.09 — только картинка; теперь RapidOCR, см. «В контуре») | 81,0 % / 81,0 % | 0 / 0 | —² | —² | — | — | 41 с |

¹ Замер на машине под посторонней нагрузкой (load average 16–19): на
свободной машине одиночный запрос в контейнере — 1,3–1,5 с (разбор кадра
0,5 с + SigLIP на CPU 0,9 с, OCR параллельно).
² Эмуляция x86 на Apple Silicon медленнее нативного CPU в 3–6 раз, её
латентность не показательна для x86-машины проверки.
³ Во втором прогоне у двух фото Yandex OCR не ответил за таймаут (сбой DNS
на машине замера): эти фото ушли без текста, одно стало промахом.

### Интерфейс и API

Все данные о винах в интерфейсе — только из каталога через API, ни одной
захардкоженной позиции.

| Экран | Что делает | Эндпоинт |
|---|---|---|
| Сканер | фото → карточка; при низкой уверенности — до 5 вариантов и аналоги по профилю снимка; при сбое — экран ошибки с повтором | `POST /scan` |
| Карточка | регион, сорт, стиль, цвет, описание, к чему подать, рейтинг (демо), ссылка на страницу портала, аналоги с причинами сходства | `GET /wines/{slug}` |
| Каталог | поиск по названию, винодельне, сорту; фильтры по стилю и региону с числом позиций | `GET /wines` |
| Винодельня | все вина хозяйства, его регионы и стили | `GET /wines?winery=` |
| Сомелье | 3 вопроса (блюдо, регион, тихое/игристое) → вина разных стилей и хозяйств, под каждым — почему подходит; если фильтры вместе ничего не дают, ослабляет их и говорит об этом | `GET /sommelier` |
| Мои вина | избранное и недавно просмотренные, localStorage | — |

`GET /wines` — `q`, `style`, `region`, `winery`, `sparkling` (признак из
названия и описания: «игристое», «брют», «петнат»), `limit` ≤ 60, `offset`.
Ответ: `{total, items: [{slug, card}], styles, regions}`.

`GET /sommelier` — `food` (обязателен), `region`, `sparkling`, `limit` ≤ 24.
Ответ: `{total, relaxed, used, items: [{slug, card, why}], regions}`.

**Функция после поиска** (`src/wine_scanner/enrich/`):

- **К чему подать.** Берётся совет винодельни из описания (156 вин), у
  остальных — правила по сахару, игристости, сорту и стилю. Заполнено у всех
  2103 позиций: в дампе такой колонки нет.
- **Рейтинг Роскачества** — демо-значение 83–95, детерминированное от slug и
  одинаковое у винтажей одного вина. В выгрузке рейтинга нет, кейсодержатель
  разрешил показать механику; в API (`rating.demo: true`) и в UI он так и
  помечен.
- **Аналоги других виноделен** подбираются по множеству сортов (Jaccard),
  стилю, сахару, региону и аромату, не больше одного вина от хозяйства. У
  каждого аналога есть причины сходства (`reasons`): «тот же сорт», «тот же
  регион».
- **Вина нет в каталоге** (`confident: false`). Аналоги строятся не от лучшего
  кандидата, который здесь заведомо неверен, а от профиля снимка: голосование
  топ-5 кандидатов по скору плюс сорт, стиль и регион, прочитанные на
  этикетке. Профиль отдаётся в `analogs_profile`.
- **Цифровой сомелье** подбирает к блюду вина разных стилей и хозяйств и
  объясняет выбор.

Статика фронта подключается с меткой версии (`styles.css?v=…` в `frontend/index.html`):
после правки CSS или JS поднимите её, иначе открытая вкладка может взять старый файл из кэша.

### Дизайн

Интерфейс в стилистике портала: палитра снята с боевого CSS vino-svoe.ru
(бордо `#8f3d42`, бумага `#fefdfa`, графит `#2c2a28`), шрифты — Playfair
Display для заголовков и названий вин, системный шрифт для текста и подписей
(Onest — в лоадере). Два
производных тона — тёмное бордо «погреба» из цвета лоадера и латунь из
портального `--gold`. Все токены — в `:root` файла `frontend/styles.css`.

- **Арка-ниша** — единственный декоративный элемент. На первом экране
  тёмная ниша с контуром бутылки и рамкой видоискателя вокруг этикетки.
  Под каждой бутылкой в карточке, каталоге и лентах — светлая ниша; белый
  фон каталожных фото растворяется в ней (`mix-blend-mode: multiply`).
- **Типографика**: Playfair Display крупным кеглем, короткие подписи капителью,
  паспорт вина — таблица на тонких линиях, варианты сомелье — простой
  список. Залита только главная кнопка «Сфотографировать».
- **Фон** — две ветви виноградной лозы с листьями, гроздьями и усиками по
  краям экрана, линией в цвете бордо (`frontend/vine.svg`, 76 КБ). На
  телефоне ветвь идёт вдоль левого края, прозрачность 6–7 %; на десктопе
  лоза лежит на полях по бокам от листа и едва проступает сквозь него,
  как через кальку. Середина, где контент, остаётся пустой.
- **Без лишнего декора**: нет свечения, орнаментов и слоганов. Тексты
  интерфейса — инструкции и данные каталога. Во время распознавания — одна
  подпись «Распознаём этикетку», без выдуманных этапов.
- **Mobile-first.** Основной сценарий — телефон: первый экран целиком
  помещается в 390×844 без прокрутки, навигация — таббар снизу.
- **Десктоп** — разворот в две колонки: приглашение и ниша, бутылка и
  карточка, список вариантов и замены. Меню — в строке с логотипом.
- **Большие мониторы.** С 1680 px разворот масштабируется целиком
  (`zoom` 1.12 / 1.3 / 1.55 на 1680 / 2100 / 2800 px) — на 1920–2560 он не
  остаётся узкой колонкой мелкого текста. Высота ниши на первом экране
  привязана к высоте окна в пределах 480–660 px.
- **Доступность**: текст не ниже 5:1 по контрасту, фокус переносится на
  заголовок нового экрана и объявляется диктору, фильтры каталога
  листаются стрелками, `prefers-reduced-motion` отключает анимации.
- **Лоадер «evolve»** (`frontend/loader.js`, `loader.css`) — перенос
  boot-экрана с evolve-scripts.online в цветах сайта: сетка точек, знак
  evolve, сегментный прогресс, шов и разъезд на две половины. Строки лога —
  ответ `/health` (каталог, индекс, эмбеддер, OCR). Показывается при
  каждой загрузке, пропускается клавишей или касанием, при «уменьшить
  движение» не показывается.

### Переменные окружения

| Переменная | Назначение |
|---|---|
| `CATALOG_PATH` | подготовленный каталог, `data/catalog.csv` |
| `CATALOG_IMAGES_DIR` | фото каталога, `data/catalog_photos` |
| `CATALOG_THUMBS_DIR` | превью фото для карточек UI, `data/catalog_thumbs` |
| `ARTIFACTS_DIR` | индекс и отчёты, `artifacts` |
| `YANDEX_API_KEY` | API-ключ Yandex Vision OCR (роль `ai.vision.user`); пусто — локальный OCR |
| `YANDEX_FOLDER_ID` | ID каталога Yandex Cloud |
| `CORS_ORIGINS` | домены портала через запятую, по умолчанию `*` |
| `CONFIG_PATH` | конфиг весов и порогов, `config/config.yaml` |
| `FRONTEND_DIR` | статика интерфейса, `frontend` |
| `MAX_UPLOAD_MB` | предел тела `/scan`, по умолчанию 100 |
| `SCAN_CONCURRENCY` | сколько `/scan` одновременно идут в модель, по умолчанию 2; 0 — без предела |
| `LOG_LEVEL` | уровень логов, `info` |
| `HOST_PORT` | порт на хосте для `docker compose`, по умолчанию 8080 |
| `INDEX_KIND` | перекрывает `index.kind` из `config.yaml`: `numpy` (по умолчанию), `faiss`, `pgvector` |
| `PGVECTOR_DSN`, `PGVECTOR_TABLE` | только при `pgvector`: строка подключения PostgreSQL и таблица (по умолчанию `wine_vectors`) |
| `VLM_API_KEY`, `VLM_BASE_URL`, `VLM_MODEL` | только для офлайн-эксперимента `scripts/eval_judge.py` (OpenAI-совместимый API); `/scan` их не использует |

Порт процесса задаётся в команде `uvicorn --port` (в Docker — 8080).
Веса сигналов, пороги, устройство (`cuda`/`mps`/`cpu`), выбор OCR — в
`config/config.yaml`.

## Замеры

```bash
python scripts/eval_offline.py --errors   # таблица конфигураций без HTTP, разбор промахов
python scripts/evaluate.py --labels data/field/labels.csv   # сквозной прогон через HTTP
python scripts/calibrate.py               # температура confidence и порог «уверенно»
pytest                                    # контракт ответа, границы слоёв, каталог, поиск
make synth                                # синтетика из фото каталога, как в CI
```

Те же шаги одной командой — `Makefile` (`make setup`, `make test`, `make run`,
`make docker`, `make docker-pg`, `make eval`).

**CI** (`.github/workflows/ci.yml`) на каждом пуше: ruff; pytest, в том числе
`tests/test_architecture.py` (границы слоёв по импортам) и pgvector на живой
базе; сборка образа из чистого клона; запрос как у `participant_test.sh`;
точность на 60 синтетических фото из каталога с порогом top-1 75 %; тот же
сервис с индексом в pgvector.

Скрипт кейсодержателя (`participant_test.sh` из папки `eval` архива кейса,
в репозиторий не входит):

```bash
bash participant_test.sh --images-dir ./queries --manifest ./queries.tsv \
  --endpoint http://127.0.0.1:8080/v1/eval/predict --output predictions.jsonl
```

## Ограничения

- **Данные.** Для обучения, индекса и эталонов используются только
  изображения из датасета кейса (уточнение организаторов от 23.09).
  Предобученные веса SigLIP 2 и YOLOv8 — модели, не изображения.
- **Локальный OCR** — RapidOCR на любой ОС (модели скачиваются при сборке
  образа), на macOS ещё Apple Vision. На полевых фото он вровень с облаком
  (96,8 %), но медленнее: p95 1,6 с против 0,8 с.
- **faiss** на macOS конфликтует с torch (две копии OpenMP) — по умолчанию
  точный NumPy-индекс, для 2 000 позиций он быстрее и точнее ANN.
- **4 позиции дампа без фото** (в индексе 2099 из 2103) и 3 фото, не похожих
  на бутылку, — в `artifacts/catalog_report.txt`. Первые находятся только по
  тексту этикетки.
- Контент каталога используется только для демонстрации решения.
  Ключи — только из ENV, `.env` в `.gitignore`. Из `data/` и `artifacts/`
  в репозиторий попадают только рантайм-файлы для Docker: `data/catalog.csv`,
  `artifacts/index.npz`, `artifacts/models/*.pt` (~8,6 МБ) и
  `artifacts/geometric_sift.npz` (SIFT эталонов, 63 МБ).

Подробно о слоях и решениях — [ARCHITECTURE.md](ARCHITECTURE.md).
